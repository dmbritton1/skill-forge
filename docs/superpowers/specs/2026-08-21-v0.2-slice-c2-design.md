# SkillForge v0.2 — Slice C2 Design: Outcome Interpretation

*Approved design from brainstorming, 2026-08-21. Parent spec: skillforge-architecture-v4.md (draft 0.7), Sections 1.1, 7, 9.1, 9.3. Consumes the detection events written by Slice C1 (`2026-08-10-v0.2-slice-c1-design.md`).*

## What C2 is

C1 writes detection events. C2 reads them and decides what they mean: which injections became uses, which anti-skills failed, and what confidence each skill has earned. Nothing in C2 observes the model directly — every input is a row C1 already writes.

The seam matters for testing. Because every input is a ledger row, all of C2 is exercisable against synthetic fixtures without running a session, which is why this slice ships before the library has real skills in it.

## Design decisions made during brainstorming

1. **No marker protocol.** C1 deferred the decision to C2 so it could be made on data rather than principle. The data now argues against it. The paired A/B benchmark (`bench/RESULTS.md`, two traps, n=6 per condition) shows matched skills changing authoring behavior 5/6 while the same-class transfer skill scored 0/6 — indistinguishable from no skill at all, despite ledger-confirmed injection every time. The failure mode that matters is not "the model used the skill and we missed it," which is what markers detect; it is "the skill arrived and the model correctly declined to apply it," which markers would also record as a non-use, exactly like the mechanical layers do. Markers buy compliance-drift measurement, a v0.3 meta-loop input, at the cost of a context-consuming instruction on every injection. Deferred again, on evidence this time. `detection='marker'` remains a legal ledger value, so v0.3 adds the protocol with no schema change.

2. **The reconciler runs on Stop and SessionEnd, not SessionEnd alone.** Stop fires at the end of every assistant turn, so the reconciler must be cheap in the common case or it taxes every turn. It is: one indexed ledger read, and zero subprocesses unless a skill injected in this session is still unresolved. The payoff is that a failure verdict lands in the turn it becomes true rather than being backdated at session end, and no data is lost when a session dies without a clean SessionEnd — a crash, a `kill`, a closed terminal.

3. **Hot tier is gated on `working`-or-better, not on `trusted`.** A hard `trusted` gate would leave the hot tier empty until a skill accumulated two clean verified uses, which for a small library means empty for weeks. `working` — one success, more successes than failures — is a low enough bar to populate the tier and a high enough one to keep a skill that has never demonstrably worked out of every session's standing context.

4. **Buckets are a SQL view, never frontmatter.** Slice A decision 4 re-quarantines a skill on any file change, so writing a confidence value into SKILL.md would quarantine the skill every time its confidence moved. The bucket lives in the ledger, is computed by a view, and is compiled into `index.json` by sync so hooks never query it.

5. **`trusted` ships as its organic half only.** Parent spec §7 requires critique-mode Tier A passed AND (executable Tier A passed OR k>=2 real-session verification successes). Tier A is slice D. C2 implements the k>=2 half; slice D ANDs in the Tier A conjunct. Until then `trusted` means "repeatedly verified in real sessions," which is strictly weaker than the spec's definition and is documented as such.

6. **No injection-to-use ratio surface.** `uses` and `injections` are both already columns of `skill_aggregates`. A consumer divides. There is nothing to build.

## Components

### 1. Confidence view — `scripts/ledger.py`

A second view alongside `skill_aggregates`, in the same `SCHEMA` string:

```sql
CREATE VIEW IF NOT EXISTS skill_confidence AS
WITH t AS (
  SELECT skill,
    COUNT(DISTINCT CASE WHEN outcome = 'success' THEN COALESCE(session, '') END)
      AS success_sessions,
    COUNT(DISTINCT CASE WHEN outcome = 'failure' THEN COALESCE(session, '') END)
      AS failure_sessions,
    MAX(CASE WHEN event_type = 'detection' THEN ts END) AS last_used
  FROM events GROUP BY skill)
SELECT skill, success_sessions, failure_sessions, last_used,
  CASE
    WHEN success_sessions >= 2 AND failure_sessions = 0
         AND (last_used IS NULL OR julianday('now') - julianday(last_used) <= 90)
      THEN 'trusted'
    WHEN success_sessions >= 1 AND success_sessions > failure_sessions THEN 'working'
    ELSE 'unproven'
  END AS bucket
FROM t;
```

The CTE exists because SQLite cannot reference a select-list alias from a sibling expression in the same SELECT.

**Confidence counts sessions, not rows.** §7 sets the organic bar at k>=2 *real-session* verification successes, and C1 dedupes verification detections per hook call rather than per session — a skill whose verification command runs twice in one session writes two success rows. Counting rows would let a single lucky session mint a `trusted` skill. Counting distinct sessions on both sides keeps the rule symmetric, and a session where a skill both succeeded and failed counts on both sides, which correctly reads as not clean. `COALESCE(session, '')` collects CLI-logged rows with no session into one bucket rather than dropping them, the conservative direction for a value that gates promotion. The columns are deliberately named `success_sessions` / `failure_sessions` so they are never confused with `skill_aggregates`'s row-counting `successes` / `failures`.

Three properties fall out of the clause ordering rather than needing rules of their own:

- **Failure knocks down harder than success bumps up** (§9.3). One failed session drops a two-session skill from `trusted` to `working`; a second drops it to `unproven`. Recovery needs successful sessions to outnumber failed ones again.
- **90-day decay is toward unknown, not toward dead** (§9.3). A stale `trusted` skill fails the freshness clause and falls through to `working`, which it still satisfies. Nothing decays to `unproven` by age alone.
- **`last_used IS NULL` is treated as fresh.** A skill with successes but no detection timestamp cannot be dated, and inventing an age to punish it is the guess the NULL-not-a-guess rule exists to prevent.

`julianday()` parses the ledger's `isoformat(timespec="seconds")` timestamps, offset suffix included. If it ever returned NULL the comparison would go NULL, the first WHEN would silently never fire, and no skill would ever reach `trusted` — a silent failure, so it gets a direct test.

**Migration note for slice D:** `CREATE VIEW IF NOT EXISTS` creates this view on existing databases but will *not* update the definition of a view that already exists. When slice D ANDs the Tier A conjunct into the bucket rule, it must drop and recreate the view in an explicit one-time migration. Doing that unconditionally on every `connect()` is rejected here: `detect.py` connects on every tool call, and DDL on every connect means a write transaction on every connect.

### 2. Reconciler — `scripts/reconcile.py` (new)

One script, registered on both Stop and SessionEnd, branching on the payload's `hook_event_name`. It holds no state of its own — everything is derived from ledger rows for the current session, which makes re-running it idempotent by construction rather than by bookkeeping.

Constants, named so they can be tuned when real usage exists:

- `MIN_ESCAPE_S = 60` — a symptom re-firing sooner than this is the same tool output echoing back through a read or a grep, not a real second occurrence.
- `RECONCILE_WINDOW_S = 900` — how long a skill's fate stays open after injection.
- `GIT_TIMEOUT_S = 1.0` — subprocess ceiling. Larger than `retrieve.py`'s 150ms because Stop runs once per turn rather than once per tool call, and only when work is pending.
- `MAX_DIFF_BYTES = 512 * 1024`.

Per invocation:

1. One `SELECT ... FROM events WHERE session = ? ORDER BY id`. Build, in Python, the per-skill picture: injection timestamp and `preexisting_fingerprint`, which detections exist, whether a reconcile verdict is already recorded.
2. If no skill needs either fingerprint credit or a verdict, return. This is the common case and it costs zero subprocesses.
3. Otherwise read `index.json` for the pending skills' `kind` and `fingerprints`, gather the diff once (§3), and settle each one.

`index.json` is the only file the reconciler reads, and it is authoritative for both questions the ledger cannot answer: whether a skill is an anti-skill, and what its fingerprints tokenize to. A skill that is missing from the index — deleted mid-session, re-quarantined by a file edit, or injected before a sync that dropped it — is skipped entirely: no credit, no verdict, no rows. Unlike the injection hooks, the reconciler never puts skill text into context, so it needs no `trust.check_text` re-check; it reads compiled metadata only and never opens a `SKILL.md`.

### 3. Usage credit from fingerprints — the truth table

A skill injected this session is **unresolved** when it has no `verification` and no `fingerprint` detection. Symptom detections deliberately do not resolve it: a symptom firing is the trap announcing itself, which is what caused the anti-skill to be injected in the first place, not evidence that the Fix was applied.

Credit is granted only when the injection event recorded `preexisting_fingerprint = 0`. A `1` means the pattern was already in the repo and a later sighting proves nothing; a `NULL` means the probe could not answer, and §9.1 requires NULL rather than a guess. Both are skipped without even being searched for, which also means a session full of unprobeable injections costs no subprocesses at all.

The diff is gathered once per invocation, not once per skill:

- `git diff HEAD --unified=0`, added lines only (`+` prefix, `+++` headers excluded), truncated to `MAX_DIFF_BYTES`.
- `git ls-files --others --exclude-standard` for new files, each read under the existing `SNAPSHOT_MAX_FILES` / `SNAPSHOT_MAX_BYTES` caps from `retrieve.py`.
- Both concatenated and passed through `patterns.tokenize` once, then matched against each pending skill's pre-tokenized fingerprints from `index.json`.

Two subprocesses per invocation regardless of how many skills are pending, versus one `git grep` per fingerprint — this is what makes per-turn reconciliation affordable. `git diff HEAD` is the source rather than a tree walk because it isolates what changed, and pre-session dirty state is already excluded by the `preexisting_fingerprint = 0` requirement.

Stop probes a skill only while `now - T_inject <= RECONCILE_WINDOW_S`, so an injection the model never acted on stops costing subprocesses after fifteen minutes instead of taxing every remaining Stop in a long session. SessionEnd probes every unresolved skill regardless of age — it runs once, so the cost bound is not at risk, and it catches a skill applied late.

Resulting table:

| Signals present | Ledger effect |
|---|---|
| `verification` detection | use, plus its outcome; no fingerprint row is written, so one skill is credited at most one use per session |
| `fingerprint` only | use, outcome NULL — presence proves application, not correctness |
| neither | no row; the injection row alone carries the negative |

### 4. Re-fire failure semantics

An anti-skill's job is to stop a specific error from recurring. The ledger records neither file nor route, so "the same error again" is defined by skill identity and time:

- **Failure** — a `symptom` detection for skill X in session S with `T_inject + MIN_ESCAPE_S <= ts <= T_inject + RECONCILE_WINDOW_S`. Written the moment it is observed, at whichever Stop sees it. The `MIN_ESCAPE_S` floor is what excludes the detection that *caused* the injection: `detect.py` logs the triggering symptom and the injection in the same hook call, microseconds apart, so without a floor every symptom-triggered anti-skill would convict itself on the evidence that summoned it.
- **Success** — written at SessionEnd when no qualifying re-fire occurred, and suppressed when the injection is younger than `MIN_ESCAPE_S`, since the model was never given a chance to fail.
- **Neither** — a symptom firing after the window is a fresh trap, not a failure of the earlier injection, and produces no outcome row.

Both verdicts are `event_type='reconcile'`, `trigger='refire'`, `detection` NULL — a verdict is not a detection — with `outcome` set. Because `skill_aggregates.uses` counts only `event_type='detection'`, a verdict feeds successes and failures without inflating the use count. A skill with any reconcile row for the session is settled and skipped on later invocations.

Regular skills get no re-fire verdict; their outcomes come from C1's verification detections, and `save_skill` already requires `verification.command` on every `kind: skill`.

### 5. Bucket-gated hot ranking — `scripts/sync.py`

Replaces the interim `(uses + injections)` ranking placeholder. `_usage_stats()` is replaced by `_confidence()`, reading `skill_confidence` inside the same catch-all guard — the last-save-timestamp tiebreak it existed for is superseded by `last_used`. A ledger failure yields an empty map, so every skill reads as `unproven`: a broken ledger empties the hot tier rather than promoting on stale data.

- **Gate:** only `working` and `trusted` skills are eligible for the hot tier. Anti-skills remain unconditionally warm (C1 decision 4) and are unaffected.
- **Order** among eligible skills, by chained stable sorts as today: bucket rank (`trusted` before `working`), then `success_sessions` descending, then `last_used` descending, then name ascending.
- **`index.json` carries `bucket`** on every entry, so `retrieve.py` pays no ledger read.

Two consequences worth stating plainly. A new install has an empty hot tier until a skill earns a success — that is the gate working, not a bug. And a `kind: preference` skill, which requires neither `verification.command` nor `symptoms:`, has no path to an outcome and will sit warm permanently; nothing currently creates one, so this is documented rather than solved.

The bootstrap path out of `unproven` does not depend on the hot tier: BM25 retrieval delivers warm skills on relevance, the model applies one, its verification command fires, and C1 logs the success. Hot is an optimization for skills that have already proven themselves, not the only way in.

### 6. Hedged wording for unproven skills — `scripts/retrieve.py`

The injection preamble varies on the compiled bucket:

- `working` / `trusted` — unchanged: `(apply if relevant)`.
- `unproven` — `(unproven — never verified in a real session; apply only if it clearly fits)`.

This is the benchmark's transfer arm addressed directly: a plausible, same-class, ledger-confirmed-delivered skill that scored 0/6 because it did not fit the bug. The hedge names the thing the model cannot otherwise know — that nothing has ever confirmed this skill working — and pushes toward declining a poor fit rather than reaching for a nearby one.

`detect.py`'s symptom-triggered anti-skill injections are **not** hedged. The symptom literally just matched in tool output, which is the strongest relevance evidence the system produces; hedging it would weaken the highest-precision channel. `triggers.json` therefore gains no bucket field.

### 7. Hook registration — `hooks/hooks.json`

Two entries added, both `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/reconcile.py"`, on `Stop` and `SessionEnd`.

## Data flow (one Stop)

```
Stop fires
  -> SELECT this session's events                        (1 indexed read)
  -> any skill unresolved, or any anti-skill unsettled?
       no  -> return                                     (common case, 0 subprocesses)
       yes -> re-fire verdicts from rows already in hand  (0 subprocesses)
           -> if any skill is in-window with preexisting=0:
                git diff HEAD + git ls-files --others     (2 subprocesses, capped)
                tokenize once, match all pending fingerprints
                -> detection/fingerprint rows
```

## Error handling

Unchanged from every other hook in the plugin: exit 0 always, print nothing on failure, never break a turn. `main()` wraps everything in a bare `except`. Git failures produce an unknown, never a false negative — if `git diff HEAD` fails (an unborn HEAD in a fresh repo, for instance) the untracked-file pass still runs; if neither can run, no rows are written at all. Ledger writes are best-effort and independent per row, so one failed insert never suppresses another.

## Testing

Plain assert functions with `__main__` runners, in the existing style. Sandbox `HOME` as the other suites do; the reconciler's git paths need a real temporary repo, built with `git init` plus a commit in `tmpdir`.

New `tests/test_reconcile.py`:

- fingerprint present in the diff credits exactly one `fingerprint` detection; a second Stop adds none
- an existing `verification` detection suppresses fingerprint credit (no double count)
- `preexisting_fingerprint` of `1` and of `NULL` both yield no credit
- a fingerprint in a new untracked file counts
- a re-fire inside the window writes one `failure`; an echo inside `MIN_ESCAPE_S` writes nothing; a detection past `RECONCILE_WINDOW_S` writes nothing
- SessionEnd with no re-fire writes `success`; SessionEnd inside `MIN_ESCAPE_S` writes nothing
- a settled skill is not re-settled on a later invocation
- non-git cwd, malformed stdin, and missing `index.json` each exit 0, print nothing, write nothing

Additions to `tests/test_ledger.py`: each bucket boundary (0/1/2 successful sessions), two successes *within one session* staying at `working` rather than reaching `trusted`, failure demotion in both steps, and a backdated `last_used` demoting `trusted` to `working` — which is also the direct test that `julianday()` parses the ledger's timestamp format.

Additions to `tests/test_sync.py`: `bucket` present on index entries; an `unproven` skill excluded from hot; `trusted` ordered ahead of `working`. Two existing tests, `test_hot_budget_overflow_goes_warm` and `test_antiskills_do_not_consume_hot_budget`, assume a skill goes hot with an empty ledger, which the gate makes false. Their fixtures gain a seeded verification success so they keep testing budget overflow and anti-skill exclusion rather than being loosened.

Additions to `tests/test_retrieve.py`: hedged preamble for an `unproven` entry, unchanged preamble for `working` and `trusted`.

## Non-goals / deferred

- **Marker protocol** — decided against on benchmark evidence (decision 1); revisit in v0.3 for compliance-drift measurement.
- **Tier A validation** (critique and executable), **capture suggestions**, **`/stats`** — slice D. `trusted` remains the organic half only until then.
- **`/consolidate`, `/audit`, holdouts, judge postmortems** — v0.3. The transfer arm's 0/6 is a standing warning for `/consolidate`: if specificity is what carries the value, generalizing sibling skills into a shared parent moves them toward the abstraction level that measured zero.
- **Threshold tuning.** `MIN_ESCAPE_S`, `RECONCILE_WINDOW_S`, and the k>=2 session bar for `trusted` are reasoned guesses. They are module constants precisely so the first weeks of real usage can correct them.
- **Volume-gated activation (§1.1)** — the parent spec's dormancy rules are not part of this slice.
