# SkillForge v0.2 — Slice D1 Design: Automatic Capture

*Approved decisions from brainstorming, 2026-08-24. Parent spec: skillforge-architecture-v4.md (draft 0.7), Sections 5, 6, 11.1, 11.2. Slice D covers Tier A validation, capture suggestions, and `/stats`; this document is the capture half only. Consumes the detection events of Slice C1 (`2026-08-10-v0.2-slice-c1-design.md`) and runs inside the reconciler built by Slice C2 (`2026-08-21-v0.2-slice-c2-design.md`).*

## What D1 is

Every slice so far assumes skills exist. Nothing has made them. The library grows only when the user remembers to type `/skillforge:learn` at the end of a session that taught something — and the user has said plainly that they will not remember.

D1 removes the remembering. The plugin watches for a specific shape in the session (repeated failures against one target, then a success), writes a finished skill draft in a detached background process, and interrupts the moment the draft is ready to ask for approval.

Everything downstream is untouched. D1 does not change validation, the secret scan, the trust registry, tiering, or the confidence buckets. It automates exactly two things: the decision to *start* a distillation, and who writes the draft. Approval still routes through `save_skill.py`, which remains the only write path into the store.

## Design decisions made during brainstorming

1. **A prepared draft, not a nudge.** The cheap version — "this looks worth capturing, want to run /skillforge:learn?" — spends the user's attention and gives them nothing to judge. Saying no requires imagining the skill that does not exist yet. A finished draft inverts that: the answer is a glance, and "no" costs one keystroke. It also moves the expensive part off the interactive session entirely.

2. **One trigger mechanism, not two.** Brainstorming named two triggers: a long struggle followed by a fix, and tests going from failing to passing. They collapse. The rule is *N consecutive failures against the same target, then a success*, with N = 2. A test suite is a target like any other, so "tests went green" fires whenever getting them green took two or more attempts. A test that passes on the first retry is not a struggle and produces nothing, which is the intended narrowing: one-shot fixes are the case where the model already knew the answer, and a skill restating it fails the novelty gate anyway.

3. **The draft is written by a detached `claude -p`, outside the session.** Drafting inside the session would either consume the user's context window or block a hook for a minute. A headless subprocess costs the session one `Popen` and nothing else. Spiked and confirmed before writing this document: `claude -p` runs on the subscription's OAuth credentials with no `ANTHROPIC_API_KEY` present, returning `{"is_error":false,...,"result":"OK"}` in 11.0s wall clock, of which 2.7s was inside the CLI and the rest process startup. This was the user's stated precondition for choosing this approach, and it holds.

4. **`--safe-mode`, not `--bare`.** Both disable hooks, which is what stops the drafter from recursively triggering SkillForge inside itself. Only `--safe-mode` keeps subscription auth: `--bare`'s own documentation states that Anthropic auth becomes "strictly ANTHROPIC_API_KEY or apiKeyHelper", and OAuth and keychain are never read. `--bare` would silently convert every draft into an API bill, or fail outright on a machine with no key. `--safe-mode` also disables skills, so the distillation contract is inlined into the prompt rather than loaded — a feature, since it makes the drafter's input fully determined by D1 rather than by whatever is installed.

5. **Delivery interrupts at Stop, using `decision: "block"`.** The user asked to be interrupted the moment the draft is ready. Hooks have no push channel into a running turn, so the earliest real opportunity is the next hook that fires — in practice the Stop at the end of the current turn, which is also the moment the user is looking at the screen. Stop supports `decision: "block"` with a `reason` fed back to the model, which then presents the draft and asks. This is bounded by the CLI's own block cap and guarded by `stop_hook_active` (see §7). The rejected alternative, delivering as `additionalContext` at the next `UserPromptSubmit`, is strictly safer and strictly worse: a draft can sit undelivered for hours if the user walks away mid-turn.

6. **No quota.** Every signal drafts. The struggle rule is narrow enough to be its own rate limit — two failures on one target is not a common accident — and an artificial cap would silently drop the signal that mattered on a day that happened to be busy. If real usage shows this is wrong, the fix is tightening the trigger, not adding a counter.

7. **Duplicate suppression is post-draft and BM25-based.** The signal knows a command, not a topic, so nothing useful can be compared against the library before the draft exists. Once it exists, the draft's own name and description are exactly the text the retrieval index is built to match. A strong BM25 hit against an existing entry discards the draft silently. Weak or partial overlap delivers anyway: two skills about the same file are usually two different skills, and a false suppression is invisible while a false delivery costs one keystroke.

8. **Discarded drafts are remembered; breadcrumbs are not.** The user asked that a rejection not stop future drafting, but that a repeat proposal for the same problem be flagged as possibly recurring. So the two kinds of state have opposite lifetimes. Tool-call breadcrumbs are per-session scratch and are deleted at `SessionEnd`. Draft outcomes are the recurrence memory and persist indefinitely, keyed by the target signature.

9. **Scope is inferred from content, defaulting to global.** Same rule the existing `distilling-skills` contract already applies at step 5, and the same default. No new mechanism.

10. **Approval goes through `save_skill.py` unchanged.** The draft is a file in a scratch directory until the user says yes, at which point it takes the identical path a `/skillforge:learn` draft takes: validate, secret-scan, write, `trust.record(..., "self")`, sync. Automatic capture changes who typed the draft, not what may enter the store.

11. **Breadcrumbs are a new table, never `events` rows.** `events.skill` is `NOT NULL` and a breadcrumb has no skill; worse, any breadcrumb carrying `outcome = 'failure'` would be counted by `skill_confidence` and corrupt the bucket of whatever name it was forced to borrow. Separate table, separate lifetime, no view reads it.

## Where this departs from parent spec §5

§5 specifies automatic capture as a `capture_check.py` Stop hook that "surfaces a one-line suggestion" — *"This looks skill-worthy (webhook setup, ~14 turns). Run /skillforge:learn?"* — and closes with the invariant: **"suggestion, never silent auto-save. Human-in-the-loop at capture is what keeps garbage out cheaply; automation squeezes friction, not judgment."**

That invariant is preserved exactly. Nothing here saves without the user seeing the artifact and saying yes. Four things about the surrounding design are different, and each was a deliberate call in brainstorming rather than an oversight:

1. **A draft replaces the one-line suggestion.** §5's suggestion asks the user to judge a skill that does not exist yet, and to pay for the judgment by typing a command. Decision 1 inverts it. The human-in-the-loop gate moves from *before* the distillation to *after* it, which strengthens it: the user now approves the actual text rather than the idea of it. What §5 forbids is the gate's removal, not its relocation.

2. **Two of §5's four heuristics ship, collapsed into one rule.** "Tests went from failing to passing" and "a long struggle followed by a fix" are the same shape and become the single struggle rule of decision 2. "Multiple non-trivial tool-use cycles" is dropped outright: it fires on ordinary work and would draft constantly. **Preference capture** — §5's third channel, watching for user corrections into `kind: preference` micro-skills — is not in D1. It needs a correction detector and the compact-block injection path with its own aging rules, which is a slice, not a component.

3. **The duplicate check runs after drafting, not before suggesting.** §5 gates the suggestion on "retrieval finds no existing skill covering the work", and §6 step 5 specifies nearest-neighbor lookup in `embeddings.db`. Slice B already replaced embeddings with BM25 over `index.json`, so the mechanism follows suit. Ordering follows decision 7: a command string is not a topic, so there is nothing meaningful to query until the draft has produced a name and a description.

4. **No `capture_check.py`.** The heuristic lives in `reconcile.py`, which is already the Stop hook, already reads the session's ledger rows once per turn, and already has the pending-work fast path a second Stop script would have to duplicate. §5 named a file before that hook existed; adding a second Stop hook now would double the per-turn floor to save nothing.

§6's "New skills enter as `status: candidate` with `confidence: 0.5`" is already superseded — C2 decision 4 moved confidence out of frontmatter into a SQL view, because any write to SKILL.md re-quarantines the skill. D1 inherits that and writes no status into the draft.

## Components

### 1. Two new tables — `scripts/ledger.py`

Added to the existing `SCHEMA` string, alongside `events`:

```sql
CREATE TABLE IF NOT EXISTS signals (
  id INTEGER PRIMARY KEY,
  session TEXT NOT NULL,
  target TEXT NOT NULL,
  ok INTEGER NOT NULL,
  ts TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_signals_session ON signals(session, id);

CREATE TABLE IF NOT EXISTS drafts (
  id INTEGER PRIMARY KEY,
  session TEXT,
  signature TEXT NOT NULL,
  name TEXT,
  status TEXT NOT NULL,
  path TEXT,
  ts TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_drafts_signature ON drafts(signature);
CREATE INDEX IF NOT EXISTS idx_drafts_status ON drafts(status);
```

`signals` is append-only scratch, pruned wholesale (§6). `drafts` is the durable record: one row per draft the system decided to attempt, surviving the session that produced it.

`status` is a small state machine, and every transition is a single `UPDATE` on one row:

| status | set by | meaning |
|---|---|---|
| `drafting` | reconciler, at spawn | a detached drafter is running |
| `ready` | drafter | validated, scanned, deduped, on disk |
| `delivered` | reconciler, at block | shown to the user |
| `saved` | `/skillforge:library` path, after `save_skill.py` exits 0 | in the store |
| `discarded` | same, on rejection | the recurrence signal |
| `duplicate` | drafter | suppressed by BM25 |
| `aborted` | drafter | novelty gate said no |
| `failed` | drafter, or the stale reaper | invalid, secret-bearing, timed out, or crashed |

`aborted` is deliberately distinct from `failed`. The novelty gate refusing to distill model-obvious knowledge is the contract working, not an error, and conflating the two would make the eventual `/stats` view read as if the drafter were broken.

Ledger helpers stay in the same shape as `log_event`: `log_signal(session, target, ok)`, `open_draft(session, signature)` returning the new row id, `set_draft_status(id, status, **fields)`. Each opens, writes, closes; each is best-effort at every call site.

### 2. Breadcrumb writer — `scripts/detect.py`

`detect.py` already runs on `PostToolUse`, already special-cases `tool_name == "Bash"`, and already extracts a pass/fail from the harness in `bash_outcome()`. The breadcrumb rides that existing branch:

```python
outcome = bash_outcome(resp)
if outcome is not None:
    _log_signal(session, target_key(command), outcome == "success")
```

`bash_outcome` returning `None` writes nothing — the same NULL-not-a-guess rule the rest of the system runs on. A tool call whose success is unknown must not be counted as either a struggle or a fix.

**The target key** is the command's tokens, space-joined, capped:

```python
def target_key(command):
    return " ".join(patterns.tokenize(command)[:TARGET_MAX_TOKENS])
```

`TARGET_MAX_TOKENS = 24`, so a heredoc or a long pipeline is bounded rather than stored whole. `patterns.tokenize` is reused rather than re-invented, so quoting and path punctuation cannot split one command into two targets.

This groups by *exact* command, which is the deliberate ceiling. `python3 tests/test_x.py` run three times groups; `pytest -x tests/test_x.py` after `pytest tests/test_x.py` does not, because the inserted flag shifts the token sequence. That is a missed signal, never a false one, and missing is the safe direction for something that spends tokens. `ponytail:` comment names the upgrade path — key on the first token plus the longest token — for when real usage shows the miss rate matters.

Cost: one INSERT on Bash tool calls with a known outcome. `detect.py` already opens a ledger connection per event on this path, so this adds one connect-write-close in the same order of magnitude as an existing detection row.

### 3. Signal detector — `scripts/reconcile.py`

The reconciler already reads this session's ledger rows on every Stop and holds no state of its own. D1 adds a second read in the same shape:

```sql
SELECT target, ok FROM signals WHERE session = ? ORDER BY id
```

Walked once in Python with a per-target consecutive-failure counter. A target whose count reaches `STRUGGLE_FAILURES = 2` and then sees `ok = 1` yields a signal at that point; the counter resets on every success. Pure function of the row list, so it tests against synthetic fixtures with no session and no subprocess — the same seam that made all of C2 testable.

Suppression, in order, before anything is spawned:

1. A `drafts` row already exists for this `(session, signature)` — one draft per target per session, regardless of how many times the struggle repeats.
2. Any `drafts` row for this session is still `drafting` — one drafter at a time, so a session of five signals cannot fan out five `claude` processes.
3. A `drafting` row older than `DRAFT_TIMEOUT_S + DRAFT_REAP_SLACK_S` (300s + 60s) is first flipped to `failed` by the same pass, so a drafter killed by a reboot cannot wedge the session permanently.

The common case — no signals — costs one indexed `SELECT` returning nothing and zero subprocesses, preserving C2's per-turn budget.

### 4. Drafter — `scripts/draft.py` (new)

Spawned detached and never waited on:

```python
subprocess.Popen(argv, cwd=cwd, stdin=DEVNULL, stdout=DEVNULL, stderr=DEVNULL,
                 start_new_session=True, env=child_env)
```

`start_new_session=True` detaches it from the hook's process group, so the hook returning does not signal it. The hook's added cost is the `Popen` itself.

The worker then, in order:

1. **Gathers evidence.** The hook payload's `transcript_path` is the source. Entries are filtered to the window between the first failure of the struggle and the success that ended it, then truncated to `EVIDENCE_MAX_BYTES = 60 * 1024`, oldest-first. Timestamp filtering is attempted first; on any parse failure the fallback is the tail of the file under the same byte cap. The whole transcript is never sent — this project's own transcript directory is 4.1 MB, which would be both slow and mostly irrelevant. `ponytail:` recency window, not semantic selection; the signal already told us which slice of the session matters.

2. **Builds the prompt.** Both distillation contracts — `skills/distilling-skills/SKILL.md` and `skills/distilling-failures/SKILL.md` — are inlined verbatim, since `--safe-mode` means nothing auto-loads. The drafter chooses `kind`, because a struggle-then-fix genuinely fits either shape: the fix is a procedure, and the two failures that preceded it are a trap with a literal error signature. The prompt closes with the output contract: emit the SKILL.md text and nothing else, or exactly `ABORT: <one-line reason>` if the novelty gate fails.

3. **Runs the model.**

   ```
   claude -p --safe-mode --no-session-persistence --output-format text --model $SKILLFORGE_DRAFT_MODEL
   ```

   Default model `sonnet`: the task is a bounded transformation with the contract supplied, not open-ended reasoning. Overridable by env var. Prompt on stdin, `DRAFT_TIMEOUT_S = 300` wall clock, killed on expiry. The child environment carries `SKILLFORGE_DRAFTING=1` (§7). The drafter is granted no tools and needs none — every input is inline.

4. **Handles `ABORT:`** → status `aborted`, nothing written, nothing delivered.

5. **Validates** with `save_skill.validate(text)`. On errors, one retry with the exact rejection strings appended to the prompt; still failing → `failed`. One retry, not a loop: a second failure means the evidence does not support a well-formed skill, and spending a third call on it is how a background process becomes a bill.

6. **Secret-scans** with `secscan.scan_text` *before the text touches disk*. Hits → `failed`, text dropped. A draft is delivered by putting its path in front of the model; a secret-bearing draft on disk is a secret queued for injection. The scan `save_skill.py` runs at the write path is the second line, not the first.

7. **Checks for duplicates** by ranking the draft's own `name` and `description` against `index.json` with the existing `retrieve.rank`. The rule is *term coverage*, not raw score: the top hit must match at least `DUP_MIN_TERMS` (3) distinct query terms, and those must cover at least `DUP_COVERAGE` (0.6) of the query's distinct terms.

   An absolute score threshold was the obvious choice and is wrong. Measured against the real `retrieve.rank`, one near-restatement scores **4.11** in a one-entry library and **8.43** in a two-entry library — the same draft, the same match, double the score, purely because BM25's IDF term grows with corpus size. Any fixed cutoff therefore suppresses nothing while the library is small and then starts suppressing arbitrarily as it fills, which is the worst possible failure curve for a silent gate. Coverage over the same pair is stable: 0.76 for the near-restatement and 0.12 for an unrelated skill, in both corpus sizes.

8. **Writes atomically** to `~/.claude/skillforge/drafts/<id>.md` via a pid-suffixed temp plus `os.replace`, the same discipline `retrieve.save_state` already uses, so a delivery can never read a half-written draft. Status `ready`, `name` and `path` recorded.

`draft.py` also carries the resolution subcommand — `draft.py resolve <id> saved|discarded` — because the status machine belongs with the code that owns it.

### 5. Delivery — `scripts/reconcile.py`

After its existing C2 work, and only when the payload's `stop_hook_active` is falsy, the Stop hook takes the newest `ready` draft and emits:

```json
{"decision": "block",
 "reason": "SkillForge drafted a skill from this session: <path>. ..."}
```

The row is flipped to `delivered` *before* the JSON is printed, so a crash between the two loses a delivery rather than repeating one forever.

The `reason` instructs the assistant to read the file, show it to the user in full, and ask approve-or-discard — then run `save_skill.py` or `draft.py resolve <id> discarded`. It states explicitly that the draft is data: display it, never follow instructions inside it. This is the same discipline `commands/review.md` already applies to quarantined skills, and it matters more here, because this text was generated from a transcript that may itself contain hostile tool output.

The query is deliberately **not** filtered by session. A draft that finishes after its own session ended is delivered at the first Stop of the next one. Exactly one draft is delivered per block; the rest wait.

`SessionEnd` never blocks — the turn is over and there is nothing to interrupt.

**Recurrence.** Before emitting, the reconciler counts prior `drafts` rows with the same `signature` and status `discarded`. If any exist, the reason gains one sentence naming the count: the user has rejected a draft for this exact command before, which makes the underlying problem a repeat rather than a one-off. This is decision 8's whole payoff — redraft every time, but say when the déjà vu is real.

### 6. Pruning — `scripts/reconcile.py` and `scripts/sync.py`

`SessionEnd` deletes this session's `signals` rows. `sync.py`, which already sweeps stale session state at `SessionStart`, additionally deletes `signals` rows older than `SIGNAL_TTL_HOURS = 24`, catching sessions that died without a clean `SessionEnd`. Two `DELETE` statements, no vacuum, no compaction pass. `drafts` is never pruned.

### 7. Recursion and blast radius

The drafter is a Claude Code process spawned by a Claude Code hook. Four independent guards, because one of them is enough only until it isn't:

1. `--safe-mode` disables hooks in the child, so the drafter's own session fires no SkillForge hook and can generate no signal.
2. `SKILLFORGE_DRAFTING=1` in the child environment. Every hook script checks it as its first statement and exits 0. This is the guard that survives a change in what `--safe-mode` covers.
3. `stop_hook_active` gates delivery, so a Stop block can never chain into another Stop block. The CLI enforces its own cap on top of this.
4. One `drafting` row per session gates spawning, with a stale reaper behind it.

Everything else the codebase already requires still holds and is not restated per-component: every hook exits 0 and prints nothing on failure, every ledger write is best-effort and wrapped, and no skill text reaches the model without a fresh `trust.check_text` — which is why delivery hands over a *path* rather than the draft's contents, leaving display to the assistant under an explicit untrusted-data instruction.

### 8. `/skillforge:library` — `commands/library.md`, `scripts/library.py` (new)

The user asked to be able to review what has accumulated. Three actions, no more:

- `library.py list` joins `index.json` entries against the `skill_confidence` view: name, kind, scope, tier, bucket, success/failure session counts, last used, path. This is where C2's buckets become visible to a human for the first time.
- Reading a skill in full is the command reading the path `list` printed — the same pattern `/skillforge:find` already uses, with the same untrusted-data framing.
- `library.py delete <name>` removes the store directory, removes the native copy, drops the `trust.json` entry, logs a `delete` event, and re-syncs. It resolves the name against the index rather than accepting a path, so no argument can point deletion outside the store. The command file requires explicit per-skill confirmation and never batches, mirroring `commands/review.md`.

Deletion removes the skill, not its history. `events` rows survive, so a name deleted and later re-saved does not silently inherit the old confidence — the ledger's own append-only property is what makes that visible rather than a special case here.

## Data flow, end to end

1. Bash tool call fails. `detect.py` writes a `signals` row, `ok = 0`.
2. It fails again on the same command. Second row.
3. The user or the model fixes it; the command succeeds. Third row, `ok = 1`.
4. The next Stop reads the session's signals, finds two failures then a success on one target, sees no existing draft for it, inserts a `drafts` row as `drafting`, spawns `draft.py` detached, and returns. The turn is unaffected.
5. `draft.py` slices the transcript, calls `claude -p --safe-mode`, validates, secret-scans, dedupes, and writes `drafts/<id>.md`. Status `ready`. Roughly a minute, entirely outside the session.
6. The next Stop with `stop_hook_active` false blocks with the draft's path and, if this signature was discarded before, the repeat count.
7. The assistant reads the draft, shows it, asks.
8. Approve → `save_skill.py` → store, trust, sync, status `saved`. Discard → status `discarded`, the file is deleted, the signature remembered.
9. `SessionEnd` deletes the session's breadcrumbs. The `drafts` row stays.

## Cost

Measured, not estimated. The spike (`claude -p --safe-mode --no-session-persistence --model sonnet --output-format json` on a one-line prompt) took 11.0s wall clock, 2.7s of it inside the CLI. A real draft carries roughly 15–30k input tokens of contract plus evidence and emits 1–2k, so the wall clock lands nearer a minute — all of it detached.

The interactive session pays: one INSERT per Bash tool call with a known outcome; one indexed `SELECT` per Stop returning nothing in the common case; one `Popen` on the rare turn that fires a signal. Nothing on this path waits on the model.

## Testing

The house convention holds: plain `def test_*()` functions with a `__main__` runner, run as `python3 tests/test_<name>.py`, no pytest.

The seams that make this testable are chosen deliberately. Signal detection is a pure function from a row list to a list of targets, so struggle sequences, interleaved targets, resets on success, and the two-failure boundary are all fixture tests. `target_key` is pure. The status machine is exercised by driving the ledger helpers directly.

The model call is the one thing that must never run in a suite. `draft.py` invokes it through a single module-level function that tests replace with a stub returning canned text — valid draft, invalid draft, `ABORT:`, secret-bearing draft, near-duplicate — so every branch of the worker is covered and no suite ever spends a token. Delivery is tested by feeding `reconcile.run` a payload with `stop_hook_active` true and false and asserting on stdout and on the resulting row status.

## Explicitly not in D1

- **Tier A validation** (critique-mode and executable) — the rest of slice D. Until it lands, C2's `trusted` bucket keeps meaning its organic half only, and D1 does not touch the bucket rule or the view.
- **`/stats`** — the remaining slice D piece. `/skillforge:library` shows the library; it is not an analytics surface.
- **Preference capture.** §5's third channel — watching for user corrections and distilling them into `kind: preference` micro-skills injected as one compact block — needs a correction detector, a block-assembly path in the retriever, and its own aging rules. That is a slice, not a component of this one.
- **Capture from a failure with no fix.** A session that never recovers produces no signal. An anti-skill needs a Fix section, and there is nothing to put in it.
- **Editing a draft before saving.** Approve or discard, per decision 1. The user can always edit the saved file afterward, which re-quarantines it and routes through `/skillforge:review` — the existing path, working as designed.
- **Any change to `save_skill.py`'s contract.** D1 adds a caller, not a rule.
