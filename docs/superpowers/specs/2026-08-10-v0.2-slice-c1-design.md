# SkillForge v0.2 — Slice C1 Design: Detection Substrate

*Approved design from brainstorming, 2026-08-10. Parent spec: skillforge-architecture-v4.md (draft 0.7), Sections 8.1, 9.1, 9.2, 9.3. Builds on Slice A (`2026-07-10-v0.2-slice-a-design.md`: ledger, trust, sync) and Slice B (`2026-07-10-v0.2-slice-b-design.md`: retrieval, tiering).*

## Slice C decomposition

Slice C as scoped in the Slice A design bundles seven pieces. They split on a clean seam — writing detection events versus interpreting them — and ship as two slices:

- **Slice C1 (this document)** — Detection substrate: `symptoms:` frontmatter, the shared pattern matcher, compiled trigger indexes, the PostToolUse hook (symptom-triggered anti-skill injection + verification outcome capture), injection-time fingerprint snapshots.
- **Slice C2** — Interpretation: Stop reconciler and truth table, symptom re-fire failure semantics, three-bucket confidence, buckets wired into hot ranking and hedge wording, and the marker protocol if C1's data shows mechanical detection leaves real uses undetected. Depends on C1.

C1 ships standalone value — the anti-skill fast path is the highest value-per-token delivery channel in the parent spec — and every C2 input is an event C1 writes.

## Design decisions made during brainstorming

1. **The marker layer is deferred to C2.** The parent spec's own truth table (§9.1) discounts marker-only signals as likely performative and counts fingerprint-without-marker as a use regardless, so markers do not decide whether a skill counts as used — the mechanical layers do. What markers uniquely buy is compliance-drift measurement, a v0.3 meta-loop input. C1 therefore ships zero-context detection only, and C2 decides on markers with C1's data in hand instead of a guess about how often fingerprints and verifications miss.

2. **No regex anywhere; one windowed token matcher for all three pattern kinds.** The parent spec already requires token-normalized matching for verifications and fingerprints (§9.1) so an added flag or a variable request ID does not silently undercount usage. Extending the same treatment to symptoms — which §8.1 describes as "strings and regexes" — removes the regex engine entirely from a blocking hook: no ReDoS exposure on model-authored patterns, no invalid-pattern crashes, no escaping rules. The cost is true alternation, which a token subsequence covers in nearly every real error signature.

3. **Symptom triggers are frontmatter, not prose.** The spec forbids parsing `verification.command` out of markdown (§9.1); the same reasoning governs symptoms. Anti-skills gain a `symptoms:` list. The library is empty, so there is no backfill path.

4. **Anti-skills leave the hot-tier competition.** Slice B let them compete for native slots as a placeholder because they had no other mid-task channel. C1 gives them their primary one (§8.1), so they are delivered by symptom trigger first and prompt retrieval second, and the hot budget goes entirely to skills.

5. **The snapshot ships in C1 even though its consumer is C2.** Unlike markers, it cannot be added retroactively — a baseline not taken at injection time is lost. Recording it now means C2's reconciler has history on day one.

## Components

### 1. `symptoms:` frontmatter — `skills/distilling-failures/SKILL.md`, `scripts/save_skill.py`

Anti-skills gain a `symptoms:` list of 1–3 literal error signatures — the machine trigger. The `## Symptom` prose section is unchanged and remains the human-readable account (literal error plus what it wrongly makes you suspect).

```yaml
symptoms:
  - "StripeSignatureVerificationError: No signatures found matching the expected signature"
  - "Webhook signature verification failed"
```

- `distilling-failures` gains a contract step to emit the field, with the same distinctiveness rule its prose already states.
- `save_skill.py` rejects `kind: antiskill` drafts with no `symptoms:` entries (mirroring `verification.command` being required for `kind: skill`), and rejects any individual entry shorter than 8 characters or fewer than 2 tokens after normalization. That is the enforcement of "never a bare `Error` or a single common word."
- List frontmatter already parses (`fingerprints:` uses it); no parser work.

### 2. Shared matcher — `scripts/patterns.py`

Two functions, three consumers (symptoms, verifications, fingerprints).

- `tokenize(text) -> [str]` — lowercase, `[a-z0-9_]+`. Quotes, whitespace, and punctuation vanish, so `express.raw({type: 'application/json'})` and `express.raw({ type: "application/json" })` produce identical token lists.
- `matches(pattern_tokens, hay_tokens) -> bool` — the pattern's tokens must appear in the haystack in order, **within a window** of `3 * len(pattern) + 8` tokens.

The window is load-bearing. An unbounded subsequence match lets `[stripe, signature]` match a file that says "stripe" on line 1 and "signature" on line 900; bounding the span keeps the gap tolerance that makes token matching worth having (added flags, variable IDs, reformatting) while refusing whole-file coincidence.

Empty pattern never matches. Patterns are tokenized once at compile time, never in a hook.

### 3. Compiled indexes — `scripts/sync.py`

Both compiled in the store walk sync already performs, from trusted skills only, rebuilt wholesale on every run — same derived-state discipline as `index.json`.

**`~/.claude/skillforge/triggers.json`** — deliberately small, because the PostToolUse hook loads it on every tool call:

```json
{
  "compiled_ts": "2026-08-10T20:00:00+00:00",
  "symptoms": [
    {"skill": "stripe-raw-body-trap", "path": "/Users/x/.claude/skillforge/antiskills/stripe-raw-body-trap/SKILL.md",
     "root": "/Users/x", "tokens": ["stripesignatureverificationerror", "no", "signatures", "found"]}
  ],
  "verifications": [
    {"skill": "stripe-webhook-integration", "root": "/Users/x",
     "tokens": ["npx", "stripe", "trigger", "payment_intent", "succeeded"]}
  ]
}
```

**`index.json` entries gain `fingerprints`** — a list of pre-tokenized patterns — so `retrieve.py` needs no second file for the snapshot.

Sync's tier assignment changes in one way: entries with `kind: antiskill` are assigned `tier: warm` unconditionally and excluded from the hot budget walk (decision 4). Every other sync semantic is unchanged.

### 4. PostToolUse hook — `scripts/detect.py`

Stdin (JSON from Claude Code) carries `session_id`, `cwd`, `tool_name`, `tool_input`, `tool_response`. Both layers run on every call.

**Verification layer** — `tool_name == "Bash"` only. Tokenize `tool_input.command`; for each matching verification pattern (root-scoped, same rule as the symptom layer below), log a `detection` event with `detection=verification`, `session`, and `outcome`:

- `failure` when the harness reports the call errored (`is_error` on the tool response)
- `success` when it reports it did not
- `NULL` when the response carries no such field

Outcome is read from the harness's own error signal only. A non-empty stderr is not treated as failure: healthy tools write to stderr routinely, and a false failure penalizes a skill that worked.

**Symptom layer** — any tool. Tokenize `str(tool_response)` truncated to 64KB, match against every symptom pattern, and for each hit:

1. Log a `detection` event (`detection=symptom`, `trigger=symptom`).
2. If the anti-skill's name is not already in this session's state file, read its body, re-verify it against the trust registry (the same check `retrieve.py` performs at injection — the index says what was trusted at compile time, not what is on disk now), and stage it for injection.
3. Emit staged bodies as `hookSpecificOutput.additionalContext` with `hookEventName: PostToolUse`, each framed `--- SkillForge anti-skill '<name>' (symptom matched in tool output): ---`.
4. Record the injected names in the session state file and log one `injection` event each (`tier=warm`, `trigger=symptom`).

Gates: max 2 anti-skills per tool call, cumulative body budget 1,200 tokens (`len(body)/4`), root-scoped exactly as retrieval is (global symptoms always eligible; project symptoms only when `cwd` is inside their root).

Session state reuses `retrieve.py`'s `load_state`/`save_state` and the same `state/session-<id>.json` file, so symptom-triggered and prompt-triggered injection share one dedupe set and the same skill cannot arrive twice through two channels.

Latency budget: <50ms on the matching path — one tokenize pass over the truncated output, patterns pre-tokenized, no subprocesses. The exception is an actual anti-skill injection, which also takes a fingerprint snapshot (Section 5) and therefore spawns `git grep` subprocesses under the same `SNAPSHOT_MAX_PROBES` ceiling as the prompt hook. That path is bounded to 2 anti-skills and fires at most once per anti-skill per session, since injection is session-deduped.

### 5. Injection-time fingerprint snapshot — `scripts/retrieve.py`

Before emitting an injection, for each of the entry's fingerprints:

1. `git grep -F -l -- <longest literal token>` in `cwd` narrows to candidate files at C speed.
2. `patterns.matches()` confirms on those files — capped at 20 files and 200KB each.

The injection event records `preexisting_fingerprint`: `1` if any fingerprint was already present, `0` if none were, `NULL` when the answer is unknown (not a git repo, `git` missing, or the 150ms subprocess timeout fired). NULL rather than a guess: a false `preexisting` silently suppresses a real usage credit later, which is the failure mode §9.1 warns about.

Per-pattern granularity is collapsed to one any() value per injection event — C2's reconciler asks "was it already there," not which one.

### 6. Ledger — no schema change

The `events` table from Slice A already carries `detection`, `outcome`, `preexisting_fingerprint`, `trigger`, and `tier`. C1 is the first writer of `detection` rows, which lights up `skill_aggregates.uses` and `last_used` — so the interim hot ranking in `sync.py` begins running on real usage instead of injections alone, with no change to the ranking code.

### 7. Hook registration — `hooks/hooks.json`

Gains a `PostToolUse` entry alongside SessionStart and UserPromptSubmit:
`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/detect.py"` (reads stdin; `cwd` comes from hook input).

## Data flow (one tool call)

```
tool call → PostToolUse hook → detect.py
  triggers.json (trusted, root-scoped)
  Bash command tokens → verification match → detection event (outcome from is_error)
  tool output tokens   → symptom match     → detection event
                                           → trust re-check → additionalContext
                                           → session state + injection event
model sees: the anti-skill for the trap it just hit, in the turn it hit it
```

## Error handling

Slice B's discipline throughout: every entry point wrapped, exit 0 always, empty output on any failure.

- Missing or corrupt `triggers.json` → no matching, no injection, exit 0.
- Malformed stdin → exit 0, no output.
- Unreadable or untrusted anti-skill body → skipped, detection event still logged.
- Ledger write failure → injection still emitted (context first, bookkeeping second), error to stderr.
- `git` missing, non-git cwd, or snapshot timeout → `preexisting_fingerprint` NULL, injection proceeds.

## Testing

Stdlib-assert files, sandbox-HOME pattern:

- `tests/test_patterns.py` — tokenizer normalizes quotes/whitespace/punctuation identically across formattings; subsequence matches with gaps (added flag, variable ID); the window rejects the tokens-900-lines-apart false positive; empty pattern never matches.
- `tests/test_detect.py` — symptom hit injects the anti-skill and logs both events; a second hit in the same session dedupes; a hit on a skill already prompt-injected dedupes across channels; tampered anti-skill body refused at injection; verification hit on a Bash command logs `detection=verification` with outcome from `is_error`, and NULL when absent; 2-per-call cap and 1,200-token budget; project symptom does not fire outside its root; 64KB truncation; corrupt `triggers.json` and malformed stdin both silent, exit 0.
- `tests/test_sync.py` additions — `triggers.json` compiled trusted-only with correct tokens; quarantined anti-skill's symptoms absent; anti-skills always warm and excluded from the hot budget; fingerprints present and pre-tokenized in `index.json`.
- `tests/test_retrieve.py` additions — snapshot records 1 when a fingerprint preexists, 0 when none do, NULL outside a git repo.
- `tests/test_save_skill.py` additions — anti-skill without `symptoms:` rejected; too-short and single-token symptom entries rejected; valid one accepted.
- E2E — sandbox HOME: save an anti-skill, sync, pipe fake PostToolUse stdin containing its error signature, verify `additionalContext`, both ledger rows, and dedupe on a second identical call.

## Non-goals / deferred

- **To C2:** Stop reconciler and truth table, symptom re-fire failure semantics (C1 writes the timestamped events; the reconciler derives re-fire rather than C1 tracking state), three-bucket confidence, buckets in hot ranking and hedge wording, marker protocol.
- **To D:** Tier A validation, capture suggestions, `/stats`.
- **To v0.3+:** ε-holdouts, judge postmortems, consolidation and staleness audit.
- Anti-skills' *preventive* value stays estimated rather than measured, per §9.1's accepted asymmetry — C1 measures rescues.
